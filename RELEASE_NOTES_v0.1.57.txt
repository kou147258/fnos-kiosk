v0.1.57 (2026-09-21)

修复：URL dashboard 还在显示旧版布局 + 「页面缩放」slider 调整整体 URL 大小

两个真实 bug 同时解决：

1. **CSS zoom reflow bug**（v0.1.53 ~ v0.1.56 一直存在，v0.1.57 修掉）：
   之前 __kioskApplyZoom 里这一行：
   ```
   root.style.zoom = userZoom;   // ← 这里
   ```
   让 `body.firstElementChild` 应用了 CSS `zoom` 属性。这个属性是非标准但
   Chromium / Firefox 都支持，**会重排 layout**（不只是 paint-scale）。
   后果：用户调 slider 到 0.5 → dashboard 容器物理变成 50% 宽 → CSS Grid
   `auto-fit, minmax(300px, 1fr)` 看到容器宽度变小 → 自动回流到 2 列。
   用户感知：「缩放 slider 调整的是整个 URL 的大小」。
   修复：删掉这一行，只剩 `transform: scale + transformOrigin: center center`。
   transform: scale 永远只 paint 缩放，不改 layout，slider 从此纯净做「Ctrl +/- 调网页内容」。

2. **URL viewport 显式锁 1920×1080**（v0.1.55 1024×768 / v0.1.56 1366×768 都不够稳）：
   v0.1.55 用 fb 物理（1024×768，4:3），dashboard CSS 在 4:3 viewport
   上触发的是「平板模式」断点（很多 dashboard 在 1024 宽度上回 2 列），
   跟桌面 reference（1280×720，3 列）布局不一致。
   v0.1.56 改成按 fb 推算 16:9 = 1366×768。但 1366 是「勉强在断点边缘」，
   仍有少部分 dashboard 在 1366 仍回 2 列。
   v0.1.57 显式锁 1920×1080，dashboard 设计尺寸绝对宽于任何 3 列断点。
   PIL cover 把 1920×1080 铺满 1024×768 fb 时：
   - scale = max(1024/1920, 768/1080) = 0.711
   - 截图变成 1365×768，居中裁切到 fb 1024×768
   - fb 上看到的是按 reference 同款字号/间距/列数排好的 dashboard，
     两侧的 dashboard 次要区域被 cover 裁掉（这些边栏在 reference 上本来
     就是次要内容，不影响 6 张核心卡片可读性）

两件事完成后，「URL 始终全屏显示」「内容可缩放」两条核心诉求同时实现：
- URL viewport 永远 1920×1080（dashboard 设计尺寸，不跟 fb、display_zoom、slider 任何一项联动）
- 「页面缩放」slider 50%-300% 通过 `transform: scale` 只 paint 缩 dashboard 内容，不 reflow
