v0.1.56 (2026-09-21)

修复：URL dashboard 卡片布局/字号/间距与桌面 reference 不一致

问题：
v0.1.55 把 URL Chromium viewport 设为 fb 物理分辨率 1024×768（4:3），以为能解掉「横压」。
实操后发现虽然不被横压，但 dashboard 的 CSS 响应式断点在 4:3 viewport 上触发的是不同列数（多数
dashboard 用 `min-width: 1200px` → 3 列，< 1200px → 2 列），导致 NAS fb 上看到的是 2 列布局（卡
片偏正方、字号偏小、间距紧），桌面 reference 是 3 列布局（卡片偏横、字号正常、间距舒展）—— 用户
体验仍然是「老样子」。

v0.1.55 这种「fb 尺寸即 viewport」的想法本质搞反了：viewport 是给 dashboard CSS 看的「设计稿尺
寸」，fb 是输出显示像素，两者本来就该解耦。

解决：
把 URL 的 Chromium viewport 改回 dashboard 的设计尺寸 1366×768（16:9），与桌面 reference 一致：

| 决策 | v0.1.55 | v0.1.56 (this) |
|---|---|---|
| Chromium viewport（dashboard CSS 看到的大小） | 1024×768（fb 物理） | 1366×768（dashboard 设计尺寸） |
| Dashboard 断点 | 4:3 → 触发 2 列布局 | 16:9 → 触发 3 列 2 行的 6 卡布局（与 reference 一致） |
| PIL cover 贴 fb0 | 1024×768 → 1024×768（无操作） | 1366×768 → 1024×768：等比 cover，左右各裁 ~171px |
| fb 显示 | 1:1 像素、布局变形 | 6 卡完整、按 reference 字号/间距渲染、左右边栏内容裁掉（这些边栏 reference 上本来就是次要内容）|
| 「页面缩放」slider | dashboard 内容 `transform: scale` | **不变，仍只缩内容不动 viewport** |

保证的两件事：
1. 「URL 始终是全屏显示」——PIL cover 永远把 Chromium 截图铺满 fb0，无黑边、无空隙（viewport 不
   管是 1366、1440、1024，最终都贴 fb）
2. 「URL 显示的内容可以放大缩小」——「页面缩放」slider 50%-300% 只对 dashboard 根元素做
   `transform: scale + transformOrigin: center center + zoom`，URL viewport 自身永不缩
